Hooks

Hooks run your own code around every decision: log decisions for review, redact personal data before the model reads it, answer repeats from a cache, count, and trace with OpenTelemetry. They run in the engine, so they apply to the Python API, the CLI, tez serve, batches and the MCP server alike.

Quick start

A hook is an object with one or more of the event methods below. Give an engine a list of them; they run in that order, around every decision it makes.

python
from tez import Cache, DecisionLog, Metrics, Redact, Tez

metrics = Metrics()
tez = Tez(backend="http://127.0.0.1:8091", template="gemma4", schemas="schemas",
          hooks=[Redact(), Cache(maxsize=4096), DecisionLog("decisions.jsonl", sample=0.1), metrics])
tez.decide("Refund to ana@example.com please", schema="support-triage")
tez.decide("Refund to ana@example.com please", schema="support-triage")   # answered by the cache
snap = metrics.snapshot()
print(snap["decisions"], snap["skipped"])                                  # 2 1

Redact comes first, so the cache key, the decision log and the model all see [EMAIL] instead of the address. The second decision is answered from the cache without a backend call.

tez serve loads hooks by name, module:object, and has a flag for the decision log. The module must be importable: the tez command does not put the working directory on Python's path, so set PYTHONPATH for a module of your own (myhooks.py is in Writing your own).

bash
PYTHONPATH=. tez serve --backend http://127.0.0.1:8091 --template gemma4 --schemas schemas \
  --decision-log decisions.jsonl --hook myhooks:RejectLongStates

Events

A hook implements any of these methods. Subclass tez.BaseHook to override only the ones you need.

EventWhenMay
on_decide_start(ctx)The request is valid, before any backend callReplace ctx.state; answer with ctx.skip(response)
on_question_end(ctx, qid, answer, meta)After each question, in the order the questions are read (state-first questions first)Read the answer and its tez block
on_decide_end(ctx)The response is built (ctx.response), also after a skipEdit ctx.response
on_error(ctx)The decision failed (ctx.error), including a request that could not be parsedObserve only
on_feedback(row)A POST /v1/feedback row is about to be writtenEdit the row in place (Redact does)

ctx.skip(response) in on_decide_start makes response the decision's answer without calling the backend, and sets its tez.latency_ms to the time actually spent. Every on_decide_start hook still runs (ctx.skipped is then true), no on_question_end fires, and on_decide_end runs as usual. Cache answers this way.

The context

tez.DecisionContext is shared by the hooks of one decision.

FieldHolds
run_id32 hex characters, the X-Tez-Run-Id and x-typesafe-request-id headers of the HTTP response. A batch item's is <batch run id>.<index>, with parent_run_id and index set
requestThe wire-format request body, as it arrived
engineThe tez.Tez deciding it
state, questions, schemaThe parsed state, {id: tez.schema.Question} and the named Schema, or None
readout, abstain, alpha, modelThe request's options; alpha after the schema's default gate
requested_layout, layoutThe layout asked for (auto, ...) and the one the questions were read in: question_first, state_first, or mixed when they differ (the X-Tez-Layout header)
response, usage, latency_msSet when the decision is done
tracesPer question: readout, layout, tokens, ms and calls, one record per backend call with its kind (letters or embed), tokens, wall ms and llama.cpp's own timings (prompt_n, cache_n, prompt_ms, ...) when the server sends them
errorThe exception, in on_error
skippedTrue after ctx.skip()
dataA dict the hooks of this decision can share
hook_errors(hook, event, exception) for every hook failure swallowed under hooks_raise=False

After a request that could not be parsed, only run_id, request and error are set, and on_error hooks must allow for that. A batch refused as a whole (no states, a bad shared field, over --max-batch) reaches on_error once, with the batch's run id and no index; a state that fails inside a batch reaches it with its own <run id>.<index>.

Hooks see the requests that reached the engine. The server answers some before that, without any hook: a body that is not JSON, is nested too deeply or is over --max-body-bytes (422, 413), a missing API key (401), a POST from a browser origin that is not allowed (403), and a wrong route or method (404, 405). Those responses still carry x-typesafe-request-id.

Order

For one call, the process-wide hooks run first (tez.set_default_hooks([...]), read at call time), then the engine's (Tez(hooks=[...]), add_hook, remove_hook), then the call's own (decide(..., hooks=[...]), handle(body, hooks=...), decide_many(..., hooks=...)). Within each list, the order given.

python
from tez import BaseHook, Tez, set_default_hooks

order = []


class Tag(BaseHook):
    def __init__(self, name):
        self.name = name

    def on_decide_start(self, ctx):
        order.append(self.name)


set_default_hooks([Tag("process")])            # every engine in this process
tez = Tez(backend="http://127.0.0.1:8091", hooks=[Tag("engine")])
tez.add_hook(Tag("added"))
tez.decide("hello", questions={"greeting": {"type": "noul", "instructions": "Is this a greeting?"}},
           hooks=[Tag("call")])                # this call only
print(order)                                   # ['process', 'engine', 'added', 'call']
set_default_hooks(None)

Put Redact first, so every later hook, the cache key and the model see the redacted state. ctx.request keeps the body as it arrived, so a hook that records anything should read ctx.state, not ctx.request["state"].

On tez serve, --hook is repeatable. A class is instantiated without arguments, a hook instance is used as it is, and any other callable is called and must return a hook. Hooks given on the command line run in the order given, and the --decision-log hook last.

Failure rules

Tez(hooks_raise=True) is the default (tez serve --hook-errors raise):

  • An exception from on_decide_start, on_question_end or on_decide_end fails the decision. The caller gets that exception, after the on_error hooks have run with it in ctx.error. Over HTTP a TezError keeps its status and type, so a hook can refuse a request with InvalidRequest (422); anything else is a 500 internal_error.
  • An exception from on_feedback fails the feedback: nothing is written.

Tez(hooks_raise=False) (--hook-errors log) is for hooks that must never fail a request, such as telemetry. An exception from any hook is logged (logger tez, warning), recorded in ctx.hook_errors and skipped; the decision and the other hooks go on. In this mode a hook cannot refuse a request.

python
from tez import BaseHook, Tez


class Broken(BaseHook):
    def on_decide_end(self, ctx):
        raise RuntimeError("the telemetry backend is down")


GREETING = {"greeting": {"type": "noul", "instructions": "Is this a greeting?"}}

tez = Tez(backend="http://127.0.0.1:8091", hooks=[Broken()], hooks_raise=False)
ctx = tez.execute({"state": "hello", "questions": GREETING})
print(ctx.response["answers"]["greeting"]["noul"])   # the decision went through
print(ctx.hook_errors)                               # [('Broken', 'on_decide_end', RuntimeError(...))]

In both modes an exception raised by an on_error hook is logged and skipped, so it never replaces the original error. Hooks run on the server's worker threads, several decisions at a time: the built-in hooks lock their own state, and yours should too.

Built-in hooks

All five are exported by tez.

DecisionLog

DecisionLog(path, sample=1.0, seed=None) appends one JSON line per decision, or a random sample share of them, in the row format tez fit and tez eval read. tez serve --decision-log PATH installs one.

json · one row of decisions.jsonl, on several lines, illustrative values
{"state": "Refund to [EMAIL] please", "labels": {},
 "predicted": {"topic": "refund", "urgent": "false", "frustration": 1},
 "decisions": {"topic": {"confidence": 0.91, "readout": "letters"},
               "urgent": {"confidence": 0.62, "readout": "letters"},
               "frustration": {"confidence": 0.48, "readout": "letters"}},
 "schema": "support-triage", "run_id": "8c91f54cfbf648bfa9ec531ea92182f1",
 "ts": "2026-09-24T19:24:54+00:00", "model": "tez-0.1.0 (gemma-4-12b-q8_0, letters)", "cached": false}

labels is empty on purpose. Review the rows, fill in the correct labels (the model's are in predicted), and pass the file to tez fit; rows left unlabelled are ignored. Fitting the model's own answers would measure the model against itself, and the gate's guarantee would rest on nothing.

bash
tez fit --schema schemas/support-triage.yaml --labels reviewed.jsonl \
  --backend http://127.0.0.1:8091 --template gemma4

A row's run_id is the decision's X-Tez-Run-Id, which POST /v1/feedback also accepts, so a correction can be traced to the decision it corrects.

Redact

Redact(patterns=None, replacement=None) replaces personal data in the state before the model reads it, and in feedback rows before they are written. The built-in patterns are email, iban, card (13 to 19 digits that pass the Luhn check) and phone (9 to 15 digits), all four by default; add regular expressions of your own. Built-ins become [EMAIL], [IBAN], [CARD] and [PHONE], your patterns [REDACTED], or all of them one fixed replacement. Strings inside object and array states are redacted and keys kept. Decisions are then made on the redacted text.

python
from tez import Redact

redact = Redact()                                    # email, iban, card and phone
print(redact.redact("Card 4111 1111 1111 1111, mail ana@example.com, call +44 20 7946 0958"))
# Card [CARD], mail [EMAIL], call [PHONE]

orders = Redact(["email", r"ORD-\d{6}"])            # a built-in and a pattern of your own
print(orders.redact({"text": "Order ORD-123456 for ana@example.com", "channel": "email"}))
# {'text': 'Order [REDACTED] for [EMAIL]', 'channel': 'email'}

Cache

Cache(maxsize=1024) answers a repeated decision from memory, keeping at most maxsize answers and dropping the least recently used. The key covers the state, every question's definition, the schema and its calibration id, the readout, abstain, the gate's alpha, the requested layout, the model alias, the backend's URL, template and model name, the embedding backend, n_probs and the default temperature, so a new fit or another model never serves an old answer. An engine reads the model name once: if you swap the model behind the same llama-server while Tez keeps running, call clear(). A cached response has tez.cached: true and zero usage. stats() returns the size, hits and misses; clear() empties it.

Metrics

Metrics(window=10000) counts decisions, errors by type, cached decisions, questions by readout, layout and gate decision, input tokens and feedback rows, with latency percentiles over the last window decisions. snapshot() returns a dict and prometheus() the Prometheus text format.

python
from tez import Metrics, Tez

metrics = Metrics(window=10_000)
tez = Tez(backend="http://127.0.0.1:8091", hooks=[metrics])
tez.decide("hello", questions={"greeting": {"type": "noul", "instructions": "Is this a greeting?"}})
snap = metrics.snapshot()
print(snap["decisions"], snap["readouts"], snap["latency_ms"]["count"])   # 1 {'letters': 1} 1
print(metrics.prometheus().splitlines()[1])                               # tez_decisions_total 1

tez serve has no metrics route. To scrape one, run the same application yourself: tez.server.create_app returns it, and a route of your own can serve the counters.

python · app.py
# app.py
from fastapi.responses import PlainTextResponse
from tez import Metrics, Tez
from tez.server import create_app

metrics = Metrics()
tez = Tez(backend="http://127.0.0.1:8091", template="gemma4", schemas="schemas", hooks=[metrics])
app = create_app(tez)                  # the application tez serve runs


@app.get("/metrics")                   # no API key check: keep this server on 127.0.0.1
def prometheus():
    return PlainTextResponse(metrics.prometheus())
bash
uvicorn app:app --host 127.0.0.1 --port 8787
curl -s http://127.0.0.1:8787/metrics

create_app applies tez serve's default request limits unless you pass limits=; see the Python API.

OpenTelemetry

OTelHook(tracer=None) opens one OpenTelemetry span per decision, tez.decide, with the attributes tez.run_id, tez.questions, tez.schema, tez.readout, tez.layout, tez.latency_ms, tez.input_tokens and tez.model, and a tez.question event per question (readout, layout, gate decision, confidence, tokens). A batch item's span also carries tez.parent_run_id and tez.index. Failures are recorded on the span. The state is never recorded.

The otel extra installs the OpenTelemetry API only; without a tracer provider the spans go nowhere. Install the SDK, or your vendor's distribution, to export them:

bash
pip install "tez-decisions[otel] @ git+https://github.com/Jibalmi/Tez" opentelemetry-sdk
python
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import ConsoleSpanExporter, SimpleSpanProcessor
from tez import OTelHook, Tez

provider = TracerProvider()
provider.add_span_processor(SimpleSpanProcessor(ConsoleSpanExporter()))
trace.set_tracer_provider(provider)

tez = Tez(backend="http://127.0.0.1:8091", hooks=[OTelHook()])
tez.decide("My invoice is wrong", questions={"billing": {"type": "noul", "instructions": "Is it about billing?"}})
# prints one span, "tez.decide", with tez.run_id, tez.layout, tez.latency_ms, ... and a "tez.question" event

OTelHook() uses the global tracer provider; pass tracer= to use another. On a server, load a small factory that sets up the provider and returns the hook, and run it with --hook-errors log, so that tracing can never fail a request:

python · tracing.py
# tracing.py
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor, ConsoleSpanExporter
from tez import OTelHook


def make_hook():
    provider = TracerProvider()
    provider.add_span_processor(BatchSpanProcessor(ConsoleSpanExporter()))   # or your OTLP exporter
    trace.set_tracer_provider(provider)
    return OTelHook()
bash
PYTHONPATH=. tez serve --backend http://127.0.0.1:8091 --template gemma4 \
  --hook tracing:make_hook --hook-errors log

Writing your own

Subclass BaseHook and override the events you need. One hook refuses long states with a 422; the other prints the llama.cpp timings of slow questions from ctx.traces.

python · myhooks.py
# myhooks.py
from tez import BaseHook, InvalidRequest


class RejectLongStates(BaseHook):
    def on_decide_start(self, ctx):
        if len(str(ctx.state)) > 20_000:
            raise InvalidRequest("state too long for this deployment")      # 422 with hooks_raise on


class SlowQuestions(BaseHook):
    def on_question_end(self, ctx, qid, answer, meta):
        trace = ctx.traces[qid]
        if trace["ms"] > 500:
            print(ctx.run_id, qid, trace["layout"], [c.get("timings") for c in trace["calls"]])
bash
PYTHONPATH=. tez serve --backend http://127.0.0.1:8091 --template gemma4 --schemas schemas \
  --hook myhooks:RejectLongStates --hook myhooks:SlowQuestions --decision-log decisions.jsonl

A hook object serves every decision, on several threads at once: keep per-decision values in ctx.data, and lock anything the hook itself holds.

Hooks on tez serve

tez serve and tez decide take the same three flags.

--hook MODULE:OBJECTrepeatable
Load a hook by name: a class is instantiated, a hook instance used as it is, any other callable called and must return a hook. Hooks run in the order given.
--decision-log PATH
Append every decision to this JSONL file, after the --hook hooks.
--hook-errors {raise,log}default raise
raise: a hook that raises fails the decision. log: it is logged and skipped.

The startup line lists the hooks it loaded, for example hooks: RejectLongStates, SlowQuestions, DecisionLog. tez-mcp takes no hook flags: when it forwards to tez serve (TEZ_URL), the server's hooks apply.
