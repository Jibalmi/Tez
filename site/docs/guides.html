Guides

How a question becomes a decision: the schema you write, how the answer is read out of the model, how to fit it to your own labels, and when it may act without a person.

Schemas

A schema is a named, reusable set of questions plus what Tez has learned about them. Put schema files in a directory, start the server with --schemas <dir>, and a request can name the schema instead of repeating its questions.

yaml · schemas/support-triage.yaml
name: support-triage
description: Route and prioritise inbound customer messages.
state: "One customer message (text)."
questions:
  topic:
    type: choice
    instructions: What is the message about?
    criteria:
      billing: Payments, payouts, invoices, refunds
      technical: Something is broken or not working
      account: Login, profile, settings
      sales: Pricing, plans, buying more
  is_urgent:
    type: noul
    instructions: Does this convey urgency?
    criteria:
      "true": Explicitly time-sensitive or blocking
      "false": No urgency expressed
  anger:
    type: score
    instructions: How upset is the writer?
    criteria: [Calm, Frustrated, Very angry]
gate:
  alpha: 0.05          # optional default for tez.gate
examples:              # optional labelled rows: the first 4 per question become few-shot examples
  - state: "I was charged twice this month."
    labels: {topic: billing, is_urgent: "false", anger: 1}

A request that names the schema needs only the state:

json · request
{"state": "I was charged twice this month.", "schema": "support-triage"}

Fields

FieldDescription
nameLetters, digits, ., _ or -; defaults to the file name. Names must be unique across the directory.
descriptionFree text for people and for GET /v1/schemas.
stateWhat a state is, for people. It is not sent to the model.
questionsMap of question id to question, in the wire format's shape.
gate.alphaOptional default gate for every request that names the schema. A request turns it off with "gate": null or false.
examplesOptional labelled rows. The first 4 labelled for a question become few-shot examples in its prompt (for questions with 26 options or fewer); the rest are training rows for tez fit. A row shown as an example is never used for fitting or measurement.

Tez reads YAML with 1.2 booleans: only true and false are booleans, so options called yes, no, on or off stay text. Worked examples in the cached prefix are measured free accuracy: four examples of the same question took the 12B from 0.704 to 0.725 on typed-decisions, with no training.

Trained artefacts

tez fit writes what it learns next to the schema, in schemas/.tez/<name>/:

  • probes.npz: per-question logistic weights on the embedding backend's features.
  • calibration.json: per question, the temperature of each readout and the conformal thresholds per alpha, with the prompt fingerprint they were fitted on.
  • manifest.json: backend, template, model, layer or cut, label counts, settings and date.

Feedback from POST /v1/feedback goes to <data-dir>/feedback/<schema>.jsonl. Editing a question's instructions, options, examples or template, or serving a different model, makes its fit stale: the question falls back to uncalibrated letters until you run tez fit again.

Readouts

A readout turns one forward pass into a probability per option. Choose one per request with tez.readout; auto uses a probe where one is trained and current, and letters otherwise.

ReadoutNeedsBackend callMeasured, typed-decisions
lettersNothing (zero-shot)/completion, one token, top-200 log-probabilities0.704 (Gemma 4 12B Q8_0)
probe25 to 50 labels per question (tez fit)/embedding (last-token state)0.793 (Qwen3.5-4B cut to 24 blocks)
blendA few labelsBoth0.766 (12B letters + 50 typical labels per question)

Letters

The prompt gives the instructions, then the options, each with a letter, then the state, and ends where the model would answer. One /completion call reads the top-200 log-probabilities of the next token; the softmax over the option letters is the distribution, divided by a per-question temperature once tez fit has calibrated it. More than 26 options run as a chunked tournament: chunks of 20 options plus "none of the options above fits", then the chunk winners meet in a final. Raw letters are poorly calibrated: ECE 0.262 on typed-decisions before a temperature, 0.067 after one.

Probe

One /embedding call returns the last-token state of the same prompt, and a per-question logistic probe trained by tez fit maps it to option probabilities. tez fit trains a probe once a question has 20 labels; the measurements say 25 to 50 per question is where a probe starts to pay. A logistic probe is fitted with a proper scoring rule, so it comes out calibrated: ECE 0.023 as read on typed-decisions.

Blend

Unless you fit with --no-blend, a probe is served blended with the zero-shot letters: weight n/(n + 10) on a probe trained on n labels and the rest on the letters, so with few labels the zero-shot prior still counts. Fifty typical labels per question on top of the 12B's zero-shot answers reach 0.766, the level of Laya's checkpoint fine-tuned on the whole train split.

With tez.abstain, the probability of __none__ comes from the letters readout even when a probe answers. Accuracy by question type and calibration for each readout are on the benchmarks page.

Fit a schema

Zero-shot letters need no labels. With labels, tez fit calibrates every question, trains probes and precomputes the gate's thresholds. The loop below is the one the measurements favour: label the most typical rows first, and keep the zero-shot answers as a prior. The examples use both servers from Run llama-server.

  1. Write the schema

    See Schemas. Save it as schemas/support-triage.yaml.

  2. Pick the rows to label

    bash
    tez suggest --schema schemas/support-triage.yaml --unlabelled inbox.jsonl --n 50 --out to-label.jsonl \
  --backend http://127.0.0.1:8091 --template gemma4 \
  --embed-backend http://127.0.0.1:8092 --embed-template qwen3

    inbox.jsonl holds unlabelled states: JSON rows with a state field, or one plain-text state per line. tez suggest embeds each state with every question's prompt, clusters the states (k-means on 32 principal components) and returns the member nearest each centre, largest cluster first.

  3. Label them

    Fill in labels on each row: an option key for a choice question, true or false for a yes/no question, the level index for a score question.

    jsonl · to-label.jsonl
    {"state": "I was charged twice this month.", "labels": {"topic": "billing", "is_urgent": "false", "anger": 1}}

  4. Fit

    bash
    tez fit --schema schemas/support-triage.yaml --labels to-label.jsonl \
  --backend http://127.0.0.1:8091 --template gemma4 \
  --embed-backend http://127.0.0.1:8092 --embed-template qwen3

    For each question, tez fit splits the labelled rows once (30 % held out, --holdout), fits a temperature for the letters, trains a logistic probe once the question has 20 labels (--min-labels) and blends it with the letters. The held-out rows are used for nothing but measurement and the gate's thresholds, so the error bound rests on decisions nothing was fitted on. It prints a table (labels, probe status, held-out accuracy of each readout, temperatures, the confidence cut at alpha 0.05) and writes schemas/.tez/support-triage/.

  5. Evaluate on rows it has not seen

    bash
    tez eval --schema schemas/support-triage.yaml --labels held-out.jsonl --alpha 0.05 \
  --backend http://127.0.0.1:8091 --template gemma4 \
  --embed-backend http://127.0.0.1:8092 --embed-template qwen3

    Accuracy, ECE and mean confidence per question, and with --alpha the share of decisions acted on and the error among them. Rows a probe was trained on are skipped unless you pass --include-seen.

  6. Serve it, and keep learning

    Restart tez serve with --schemas schemas: requests that name the schema use its probes and calibration. When a person corrects a decision, send the right label to POST /v1/feedback; the next tez fit reads those rows too (--no-feedback ignores them).

What the measurements say about labels (typed-decisions, probe on layer 26 of the frozen Qwen3.5-4B, 3 seeds): random rows reach 0.707 with 25 labels per question and 0.741 with 50; the most typical rows first reach 0.734 with 25; typical rows on top of the 12B's zero-shot answers reach 0.766 with 50. The 12B alone scores 0.705 with no labels. See the chart.

The gate

Ask for a gate and every answer also says act or escalate. The gate is conformal selection (Jin and Candès, 2023): it chooses which decisions to act on so that the expected share of wrong ones among them stays at or below a target alpha.

json · request
{"state": "I can't log in since this morning.", "schema": "support-triage", "tez": {"gate": {"alpha": 0.05}}}

The same gate is gate: {alpha: 0.05} in a schema, --alpha 0.05 on tez decide, or alpha=0.05 in Python.

How it decides

For a decision with confidence c, the conformal p-value of "this decision is wrong" counts the held-out calibration decisions that were wrong with confidence at least c: (1 + that count) / (number of calibration decisions + 1). Benjamini–Hochberg at level alpha over the held-out decisions gives one confidence cut per question and alpha, which tez fit stores. At request time Tez acts when the answer's top probability reaches the cut, and escalates otherwise.

What it guarantees, and what it needs

  • A bound on the expected error rate among acted decisions, when live traffic resembles the held-out rows. It does not bound any single batch, and it does not survive a shift in traffic or an edited question: fit again when either changes.
  • A fitted calibration. A question without one, and any __none__ answer, always escalates when a gate is requested.
  • A conservative alpha. Thresholds exist for alpha 0.01, 0.02, 0.05, 0.1, 0.15, 0.2, 0.25, 0.3 and the schema's default; a value in between uses the largest one below it.

Measured on typed-decisions, over 50 random calibration splits: at a 5 % bound a probe acts on 40 % of decisions with a realised error of 5.2 %, and the 12B's zero-shot letters act on 24 % at the same realised error. What escalate means is yours to choose: a person, a larger model, or another question. The cold-start measurements favour also sending a small random slice of acted decisions to people, so the labels you collect are not only the hard cases. See the chart.

Streaming and voice

Tez was built and measured on a voice loop: 220 spoken commands over 16 actions, decided word by word as the transcript grows. Three things make it fast and safe.

  • Options cached, message last. The action list is the constant prefix and the transcript is the only new text per word. With --swa-full the 12B spends 30 ms of compute per streamed word (45 ms round trip), evaluating 11 tokens where the transcript-first layout needs 358.
  • Re-decide on every word. Send the partial transcript as the state each time a word arrives; the cached prefix keeps each call cheap.
  • A confident none on a partial transcript means keep listening. Early in a sentence the right answer is often "none of these yet". Read it as "wait for more words", never as "do nothing".

Actions then fire by class: a cheap, reversible action such as opening an app fires on one confident partial; media and play actions need the same answer on two consecutive partials; typing and closing wait for the end of the utterance. Measured: 1 harmful action in 198 utterances, the first action on average at word 3.6 of 5.4, and Notepad open 652 ms into "open notes and type hello world", 1.3 s before the speaker finished.

The policy lives in your client; Tez answers each partial. A sketch with part of the measured action set:

python
from tez import Tez

tez = Tez(backend="http://127.0.0.1:8091", template="gemma4")
ACTION = {
    "type": "choice",
    "instructions": "Which action does the speaker want?",
    "criteria": {
        "open_notes": "Open the notes or notepad application.",
        "type_text": "Type the dictated text into the app that is currently in focus.",
        "play_spotify": "Play a specific song, artist, album or playlist on Spotify.",
        "none": "Out of scope: chit-chat, a question, or a request for something the assistant cannot do.",
    },
}
FIRE_NOW = {"open_notes"}      # cheap and reversible: one confident partial
TWICE = {"play_spotify"}       # the same answer on two consecutive partials
AT_END = {"type_text"}         # needs the whole utterance


def on_words(transcript, seen, final=False):
    """Call on every ASR partial; returns an action to run, or None to keep listening."""
    answer = tez.decide(transcript, questions={"action": ACTION})["answers"]["action"]
    choice = answer["choice"]
    seen.append(choice)
    if choice == "none" or answer["probabilities"][choice] < 0.9:
        return None            # a confident none on a partial means keep listening
    if choice in AT_END and not final:
        return None
    if choice in TWICE and seen[-2:] != [choice, choice]:
        return None
    return choice

The measured policy is experiments/stream_policy.py, and the whole loop with speech recognition is experiments/voice_demo.py. Out-of-scope speech that starts like a command ("youtube is down again") is the remaining risk: it is a property of language, handled by firing cheap actions first.
