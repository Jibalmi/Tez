API reference

Tez speaks TypeSafe's /v1/systemone wire format, so a client written for Jev's wire format, JevBench's own runner included, can point its base URL at a Tez server. Everything Tez adds lives in optional fields that strict clients ignore.

Base URL and authentication

Default address: http://127.0.0.1:8787. Without --api-key any Authorization: Bearer <token> is accepted and none is required. With --api-key (or TEZ_API_KEY), every endpoint except /healthz needs Authorization: Bearer <key> or an x-api-key header.

MethodPathPurpose
POST/v1/systemoneDecide: one state, many typed questions (Jev-compatible)
POST/v1/systemone/batchTez: many states against the same questions, in one request
POST/v1/planTez: what a /v1/systemone request would do, without calling the model
GET/v1/modelsList model aliases (Jev-compatible)
GET/healthzLiveness, backend and readout status
GET/v1/schemasTez: schemas loaded from --schemas and --presets
GET/v1/schemas/{name}Tez: one schema (questions, probe status, calibration)
POST/v1/feedbackTez: record a correct label for a past decision (feeds tez fit)

Browsers and CORS

Browsers may call the server only from listed origins. The defaults are pages served from this machine on any port, http://127.0.0.1:* and http://localhost:*, and the website's playground, https://jibalmi.github.io. Requests without an Origin header (curl, SDKs, other servers) are not affected.

  • A CORS preflight from an allowed origin is answered with the allowed methods and headers, and with Access-Control-Allow-Private-Network: true, which Chrome's Private Network Access needs before a public page reaches a server on your machine. A preflight from any other origin gets 403.
  • Every POST (/v1/systemone, /v1/systemone/batch, /v1/plan, /v1/feedback) from an origin that is not allowed gets 403 forbidden before anything runs. A page elsewhere could not read the answer anyway, but a plain cross-site form or text/plain POST would otherwise still use the model, run the hooks or write training labels.
  • Browsers send Origin on every POST, so a browser app behind a same-origin reverse proxy still needs its origin in the list.
  • A page reached through DNS rebinding sends its own origin, so its POSTs are refused too, but it can read the GET routes (schemas, models, health). Beyond this machine, run with --api-key.
bash
curl -s http://127.0.0.1:8787/v1/systemone -H "Origin: https://example.org" \
  -H "Content-Type: application/json" \
  -d '{"state": "hi", "questions": {"q": {"type": "noul", "instructions": "Is this a greeting?"}}}'
json · 403 response
{"error": {"type": "forbidden", "message": "origin https://example.org may not request decisions (allowed: http://127.0.0.1:*, http://localhost:*, https://jibalmi.github.io; tez serve --cors-origins)"}}

--cors-origins LIST (or TEZ_CORS_ORIGINS) replaces the list: comma-separated origins, host:* for any port, https://*.domain for its subdomains (not the bare domain), null for file:// pages, or * for any origin. --no-cors sends no CORS headers and allows no origin. Keep https://jibalmi.github.io in a list of your own if you use the playground.

bash
tez serve --backend http://127.0.0.1:8091 --template gemma4 \
  --cors-origins "http://localhost:*,https://jibalmi.github.io,https://*.example.com"

POST /v1/systemone

Decide one state against many typed questions. The request body:

FieldTypeDescription
statestring, object, arrayRequired. The input to decide on. Objects and arrays are serialised as JSON, and may nest at most 100 levels of objects and arrays. tez serve caps a state at 50,000 characters (Limits).
questionsobjectMap of question id to question. Required unless schema names a loaded schema, whose questions are then used, or json_schema is given.
questions.{id}.typestringnoul (yes/no), choice (2 to 255 options) or score (2 to 10 ordered levels).
questions.{id}.instructionsstring, object, arrayRequired. What to decide.
questions.{id}.criteriaobject or arraychoice: label to description or null. score: a list of level descriptions, level i = index i. noul: optional {"true": …, "false": …}.
modelstringAny string; tez-latest is the default alias, and jev-latest is listed too.
schemastringTez. Name of a loaded schema. Questions with the same id and definition use that schema's trained probe and calibration.
json_schemaobjectTez. A JSON schema of the object you want back, in place of questions; see Structured extraction.
tez.readoutstringTez. auto (default: the probe when one is trained and current for the question, otherwise letters), letters or probe.
tez.abstainbooleanTez. Adds an implicit __none__ option ("none of these fits") to every choice question. Default false.
tez.gate.alphanumberTez. Target error rate among acted decisions, between 0 and 1. Each answer then gets act or escalate; see The gate.
tez.layoutstringTez. auto, question_first or state_first. Default: the schema's layout:, else the server's --layout, else auto; see Prompt layouts.

The Tez extensions together:

json · request extensions
{
  "schema": "support-triage",
  "tez": {
    "readout": "auto",
    "abstain": false,
    "gate": {"alpha": 0.05},
    "layout": "auto"
  }
}

modelstringtez-<version> (<model>, <readouts used>).

Response headers

Every response, errors and CORS preflights included, carries:

  • x-typesafe-request-id: 32 hex characters. For a decision it is the run id that hooks see (ctx.run_id), that a DecisionLog row records and that POST /v1/feedback accepts as run_id; for other routes a fresh id.
  • server-timing: total;dur=<ms>. A decision adds tez;dur (the engine) and backend;dur (time in model calls): tez;dur=0.9, backend;dur=0.4, total;dur=2.4. A batch adds tez;dur only.

Decisions that reach the engine, successful or not, also carry X-Tez-Run-Id, the same id. A 401, a 403, and a body over --max-body-bytes or not JSON are answered before that, without it. A single decision that got that far carries X-Tez-Layout too: question_first, state_first, or mixed when its questions were read in different layouts. Browsers from allowed origins can read all four headers.

bash
curl -s -D - -o /dev/null http://127.0.0.1:8787/v1/systemone \
  -H "Content-Type: application/json" \
  -d '{"state": "My invoice is wrong and I need it fixed today.", "schema": "support-triage"}'
output, abridged
HTTP/1.1 200 OK
content-type: application/json
x-typesafe-request-id: 7218d0bce2514605b08f520278062bb8
server-timing: tez;dur=0.9, backend;dur=0.4, total;dur=2.4
x-tez-run-id: 7218d0bce2514605b08f520278062bb8
x-tez-layout: state_first

Answer shapes

The three answer shapes are exactly Jev's:

TypeFieldsMeaning
noulnoulP(yes). No confidence: Jev's noul answers carry none.
choicechoice, probabilities, confidenceThe argmax label, a probability per label (they sum to 1), and confidence = (k·pmax − 1)/(k − 1) for k options: 0 when uniform, 1 when certain.
scorescore, legend, probabilities, confidenceThe expected level Σ i·pi, the level descriptions keyed by level string, a probability per level string, and confidence as for choice.

With tez.abstain, a choice answer can be __none__, with its own probability.

The tez block

latency_ms, and per question the readout used, a decision when a gate applies, p_correct with calibration_id when a fitted calibration exists, temperature when a default temperature was used and layout when the layouts are mixed.

  • The gate never acts without evidence: act always comes with p_correct and calibration_id. A question with no usable fitted calibration, and any __none__ answer, gets escalate whenever a gate is requested.
  • tez.gate: null or false turns a schema's default gate off; tez.gate: {} uses the schema's default alpha.
  • Thresholds are precomputed for alpha 0.01, 0.02, 0.05, 0.1, 0.15, 0.2, 0.25, 0.3 and the schema's default; any other alpha uses the largest precomputed value at or below it.
  • tez.readout: "probe" is strict: the request fails with 422 if a requested question has no usable probe. auto falls back to letters question by question.
  • A fit is used only while the question's prompt (instructions, options, few-shot examples, template, layout) and the model still match what tez fit saw. Otherwise the question falls back to uncalibrated letters and GET /v1/schemas/{name} marks it stale. Under auto a fitted question is read in the layout it was fitted under.
  • An unfitted letters answer of Gemma 4 12B Q8_0 is read at a default temperature. No argmax changes, but a yes/no probability moves towards 0.5 without crossing it, and a score question's score moves towards the middle of the scale while its most probable level stays the same. For an integer level, take the most probable level from probabilities, or run with --default-temperature off.

Errors

The same codes as Jev, and a few more, with one body shape: {"error": {"type": "…", "message": "…"}}. Messages name the offending field or limit.

StatustypeWhen
401unauthorizedThe server runs with --api-key and the request has no valid key.
403forbiddenA POST, or a CORS preflight, from a browser origin that is not allowed (Browsers and CORS).
404not_foundUnknown route, or GET /v1/schemas/{name} for a schema that is not loaded.
405method_not_allowedWrong method for a route.
413payload_too_largeA request over the server's limits: body size, questions, state length or batch size. A json_schema counts its questions while it is expanded, so a small schema whose references multiply them is refused early; more than 10,000 references, or more than 1,000,000 characters of copied definitions, is refused too.
422invalid_requestThe request does not match the contract, tez.readout: "probe" for a question without a usable probe, a json_schema Tez cannot decide, a state nested more than 100 levels, a number that is not finite (NaN, Infinity, 1e400) or a string with an unpaired surrogate anywhere in the body (refused before any hook or model call), or a prompt longer than the model's context (with llama.cpp's message).
500internal_errorAn unexpected failure, for example a hook that raised something other than a TezError.
503backend_unavailableThe model server is unreachable, still loading or failed.
json · 422 response
{"error": {"type": "invalid_request", "message": "questions.q.type must be one of noul, choice, score; got 'multi'"}}

Structured extraction

In place of questions, a request may carry json_schema, a JSON schema of the object you want back. Tez turns its fields into questions (enums into choices, booleans into yes/no, small integer ranges into scores), decides them like any others and returns the object in tez.values. The answers are in answers too, keyed by each field's dotted path.

bash
curl -s http://127.0.0.1:8787/v1/systemone \
  -H "Content-Type: application/json" \
  -d '{
  "state": "Charged twice for invoice 4411, please fix it today!",
  "json_schema": {"type": "object", "properties": {
    "department": {"enum": ["billing", "technical", "sales"], "description": "Which team should handle it?"},
    "urgent": {"type": "boolean", "description": "Does it need a reply today?"},
    "priority": {"type": "integer", "minimum": 1, "maximum": 3, "description": "How important is it?"},
    "refund": {"anyOf": [{"enum": ["full", "partial"]}, {"type": "null"}],
               "description": "Which refund does the customer ask for?"}}}
}'

The response's tez.values for that request has this shape (which values come back depends on the model):

json · tez.values
{"department": "billing", "urgent": true, "priority": 3, "refund": null}

json_schema and questions cannot both be given; schema may name a loaded schema whose identical questions then use its fits. A schema Tez cannot decide in one pass (free strings, arrays, integer ranges over 10 values) is refused with a 422 that names the path. The mapping, the Python helpers and the gate are in Structured extraction.

POST /v1/systemone/batch

Many states against the same questions. The body is a /v1/systemone request with states, an array, in place of state; questions (or schema or json_schema), model and tez apply to every state.

bash
curl -s http://127.0.0.1:8787/v1/systemone/batch \
  -H "Content-Type: application/json" \
  -d '{"states": ["My invoice is wrong", {"text": "the app crashes on start", "plan": "Business"}],
       "schema": "support-triage"}'
json · response, abridged
{"model": "tez-0.1.0 (gemma-4-12b-q8_0, letters)",
 "results": [{"model": "...", "answers": {"...": "..."}, "usage": {"...": "..."}, "tez": {"...": "..."}},
             {"error": {"type": "invalid_request", "message": "state must be a string, object or array"}}],
 "usage": {"input_tokens": 991, "output_tokens": 0},
 "tez": {"latency_ms": 431.6, "run_id": "7dff261d74b04edcbe80578818697177"}}
  • results has one entry per state, in input order: the state's /v1/systemone response, or {"error": {"type", "message"}} for a state that failed. One state's error never fails the others; a state over --max-state-chars is that state's 413 error.
  • A bad shared field fails the whole batch with 422, and more states than --max-batch or more questions than --max-questions with 413. When the backend is unavailable before any state was decided the batch fails with 503; once some states are decided, the ones not yet tried get a backend_unavailable error without calling the backend again.
  • Each state's questions run back to back (state first with two or more questions), so the prompt cache keeps the state between them. States are decided one after another.
  • usage sums the decided states. tez.run_id is the batch's run id, also X-Tez-Run-Id; state i is decided with run id <run_id>.<i>.

POST /v1/plan

The body of a /v1/systemone request, state optional; nothing is sent to the model. Per question: the readout it would use, its fit (ready, stale or none, with the reason, the fit's layout and calibration id), the number of options, the backend calls, the layout, the prompt hash (prompt_sha, what tez fit records) and a token estimate (characters / 4), with the prefix the prompt cache would keep from the question read just before it. The top-level layout is the one the questions share, or mixed; order is the order they would be read in.

bash
curl -s http://127.0.0.1:8787/v1/plan \
  -H "Content-Type: application/json" \
  -d '{"state": "My invoice is wrong and I need it fixed today.", "schema": "support-triage"}'
json · response, abridged
{"backend": "http://127.0.0.1:8091", "template": "gemma4", "model": null, "schema": "support-triage",
 "readout": "auto", "requested_layout": "auto", "layout": "state_first", "state_tokens": 12,
 "order": ["topic", "urgent", "frustration"],
 "questions": {"topic": {"type": "choice", "options": 7, "layout": "state_first", "readout": "letters",
                         "fit": {"status": "none", "reason": "not fitted (tez fit --schema support-triage)"},
                         "calls": {"letters": 1, "embed": 0}, "prompt_sha": "2bf4e9664164e25b",
                         "prompt_tokens": 214, "cached_tokens": 0},
               "urgent": {"type": "noul", "options": 2, "layout": "state_first", "readout": "letters",
                          "fit": {"status": "none", "reason": "not fitted (tez fit --schema support-triage)"},
                          "calls": {"letters": 1, "embed": 0}, "prompt_sha": "c87a390957050bb8",
                          "prompt_tokens": 135, "cached_tokens": 59},
               "frustration": {"...": "..."}},
 "totals": {"calls": {"letters": 3, "embed": 0}, "prompt_tokens": 503, "cached_tokens": 118, "evaluated_tokens": 385},
 "notes": ["state first: 3 questions read back to back, each after the first reusing the prefix it shares with the one before (cached_tokens; needs llama.cpp prompt caching on one slot, --swa-full for Gemma)",
           "model names not checked (the plan does not call the backend): a fit made on another model would not be used"]}

A question that would fail (tez.readout: "probe" without a usable probe) has "readout": null and an error instead of failing the plan. Model names are compared only once the server knows them (model is null until a decision has asked the backend), and a note says so. tez plan prints the same as a table (--json for this body).

Other endpoints

GET /v1/models

json · response
{"models": [{"name": "tez-latest", "description": "Tez local decision engine (gemma-4-12b-q8_0, letters)",
             "release_date": "2026-09-24"},
            {"name": "jev-latest", "description": "Alias of tez-latest: Tez local decision engine (gemma-4-12b-q8_0, letters)",
             "release_date": "2026-09-24"}]}

jev-latest is listed so that clients written for TypeSafe's SDK, which look a model up by that name, find it. Every alias, and any other model string, is decided by the same engine.

GET /healthz

json · response
{"status": "ok", "version": "0.1.0", "backend": "http://127.0.0.1:8091", "template": "gemma4", "backend_status": "ok",
 "model": "gemma-4-12b-q8_0", "embed_backend": null, "schemas": ["support-triage"], "probes": {"support-triage": ["topic"]},
 "layout": "auto"}

status is degraded when the backend is unreachable (backend_status: "unreachable"). With a separate embedding backend, embed_template and embed_backend_status are added. layout is the server's default prompt layout (--layout). /healthz needs no key.

GET /v1/schemas and /v1/schemas/{name}

json · GET /v1/schemas
{"schemas": [{"name": "support-triage", "description": "...", "questions": {"topic": "choice", "urgent": "noul"},
              "calibration_id": "support-triage@2026-09-24", "probes": ["topic"], "builtin": false}]}

builtin is true for a preset loaded with tez serve --presets. One schema returns its questions in wire form plus layout (the schema's own, or null), served_layout (what a request that names none gets), calibration_id, probes (per question: probe is ready, stale or none, with letters_calibrated, n_labels, a note and the layout it was fitted under), calibration and manifest.

POST /v1/feedback

bash
curl -s http://127.0.0.1:8787/v1/feedback \
  -H "Content-Type: application/json" \
  -d '{"schema": "support-triage", "question": "topic", "label": "billing",
       "state": "Help! My payouts have been failing for 3 days.",
       "run_id": "7218d0bce2514605b08f520278062bb8"}'

Records the correct label for a past decision. run_id is optional: the decision's X-Tez-Run-Id, stored with the row. Tez appends the row to <data-dir>/feedback/<schema>.jsonl (by default the schema file's directory plus /.tez; for a preset, the first --schemas directory's .tez, else ./.tez) and answers {"ok": true, "schema": …, "question": …, "label": …}. on_feedback hooks see the row first (Redact removes personal data from its state). tez fit trains from these rows plus any labelled file.

Limits

tez serve refuses oversized requests with 413 payload_too_large:

FlagDefaultLimit
--max-body-bytes2 MiB (2,097,152)Request body. A Content-Length over it is refused before reading, a chunked body as soon as it passes it.
--max-questions64Questions per request, and per batch
--max-state-chars50,000Characters per state; an object or array counts as its JSON
--max-batch64States per /v1/systemone/batch request
bash
tez serve --backend http://127.0.0.1:8091 --template gemma4 \
  --max-state-chars 20000 --max-batch 16
json · 413 response to a 25,000-character state
{"error": {"type": "payload_too_large", "message": "state is too large: 25,000 characters (the limit is 20,000; tez serve --max-state-chars)"}}

0 switches a limit off. A state may also nest at most 100 levels of objects and arrays (422). The MCP server applies the same defaults. In Python, Tez.handle, execute, handle_batch and plan apply none unless given limits=tez.config.Limits(...), while tez.server.create_app applies these defaults unless given other limits.
